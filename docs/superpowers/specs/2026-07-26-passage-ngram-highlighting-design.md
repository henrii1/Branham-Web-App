# Passage N-gram Highlighting

**Date:** 2026-07-26
**Status:** Approved

## Problem

The Sources/Passages panel (`SourcesPanel.tsx`) shows the aggregated sermon paragraphs retrieved by BM25 + dense search (`ragData.ragContext`), rendered as plain prose with no visual indication of *why* a given passage was retrieved or which part of it actually relates to the query. Users have to read the whole passage to find the relevant part themselves.

## Goals

- Highlight the substrings within each retrieved passage that directly overlap with the query, using n-gram comparison.
- Apply consistently everywhere passages are shown — both the live chat UI (`ChatShell`) and the public SEO answer pages (`SeoShell`), since both render through the same shared `SourcesPanel` component.
- Keep matching conservative: because passages come from a mix of keyword (BM25) and semantic (dense) retrieval, many relevant passages will share no literal wording with the query at all — that's expected and fine. The feature only highlights literal overlap; it is not a relevance indicator for semantic-only hits.

## Non-Goals

- No stemming, fuzzy matching, or semantic similarity scoring — purely literal, contiguous, word-level n-gram overlap.
- No changes to the Python RAG API or to `rag_context`'s markdown format — this is entirely a client-side rendering concern, operating on data already delivered today.
- No highlighting in the final chat answer panel (that panel already has its own citation-pill styling via `applyCitations`; this feature is Sources-panel-only).

## Matching Algorithm

**Input query text**: `ragData.retrievalQuery` — the already-normalized query actually used for BM25/dense retrieval (not the raw, unnormalized user input). This is already available on the existing `RagData` type (`src/lib/chat/types.ts`).

**Normalization** (applied to both query and passage text, comparison-only — the original passage text is what gets displayed/highlighted, never the normalized form):
1. Unicode-normalize (NFKD) and strip combining diacritical marks, so e.g. `café`/`cafe` compare equal — relevant given the app's ES/FR support.
2. Lowercase.
3. Strip punctuation.
4. Split on whitespace into a word-token list, preserving original-text offsets per token so matches can be mapped back to the unmodified source string.

**Match rule**: A span is highlighted only where **3 or more consecutive words**, in the same order, appear in both the query's token list and the passage's token list (a minimum-3 contiguous-run match, not a fixed-size sliding window). Runs of 1–2 words are treated as noise and ignored. This keeps matching precise without needing a stop-word list.

**Algorithm shape**: for each passage, compare its token list against the query's token list using a greedy contiguous-match scan (for every `(i, j)` pair where `passage[i] == query[j]`, extend the match while both sequences continue to agree; keep matches with length ≥ 3). Overlapping/adjacent qualifying runs are merged into a single continuous highlighted span. Both lists are short (a handful of query words; a paragraph-sized passage), so this is cheap — no need for a general LCS/suffix-array approach.

## Rendering Integration

`renderMarkdown` (`src/lib/markdown/render.ts`) strips all raw HTML from its markdown input (its custom `html()` renderer always returns `""`) — so highlighting **cannot** be injected before markdown rendering. It has to work the same way `applyCitations` already does for the chat answer panel: as a post-processing pass over the *already-rendered* HTML string, generated by our own code (not parsing arbitrary external HTML), so it's safe.

New module: `src/lib/markdown/ngramHighlight.ts`, exporting `applyNgramHighlights(html: string, query: string): string`.

- Splits the HTML string into alternating tag/text segments (same technique `citations.ts` uses on the chat panel), tracking whether the current position is inside a heading (`<h1>`–`<h6>`) so sermon title/section headers are never highlighted — only actual passage body text is eligible.
- Within eligible text segments, applies the matching algorithm above and wraps qualifying spans in `<mark class="passage-highlight">...</mark>`.
- Styled as a subtle background-color highlight (distinct from the chat panel's `citation-pill` styling, so the two don't visually collide), themed for both light and dark surfaces.

**Wiring** (`SourcesPanel.tsx`): extend the existing memoized pipeline —
```ts
const renderedHtml = useMemo(() => {
  if (!ragData) return "";
  const cleaned = postprocessRag(ragData.ragContext);
  const html = renderMarkdown(cleaned);
  return applyNgramHighlights(html, ragData.retrievalQuery);
}, [ragData]);
```
No new re-render cost beyond what's already memoized per `ragData` change.

- Any backend/RAG-pipeline change.
